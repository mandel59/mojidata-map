# 絵文字一覧のレイアウトとページ送り

2026-09-25。絵文字一覧を文字マップと同じ密度にそろえ、ページ送り時のセル再生成と不要な走査を削減した。

この記録の比較値は1ページ120件の時点のもの。後続の変更で1ページ64件とした。現在の計測スクリプトは実際のページ件数も `pageSize` に記録する。

## 変更

- 文字マップとセルCSS・文字サイズの表示ホストを共有する。標準サイズ30pxではセル高97→56.5px。1024×600の一覧は16列、390×600では8列になり、実測で文字マップのセルと幅・高さが一致した。
- 大きな見出し・説明を省き、検索欄＋表示設定、件数＋グループ選択、ページ送り＋Emoji版の順に整理した。一覧だけをスクロールし、操作欄は残す。名前は1行で省略し、全文はツールチップと詳細欄で確認できる。
- 120件の表示枠をページ内位置で再利用する。名前、字形、選択状態、タイトル、挿入処理を一緒に更新する。全件置換がなくなり、20回のページ変更でセルの追加・削除はそれぞれ2,400→0件。
- グループ候補と表示中のページをメモ化する。Page Up/Downの選択位置は全結果ではなく表示中の120件だけから求め、選択コード列の連結も一度にする。

## 測定方法

`npm run build` の後、`node tools/benchmark-emoji-pages.mjs [ビルドディレクトリ]` で測る。変更前は `d09a718c` のビルドを `var/emoji-pages-before-dist/` に保存。幅1024pxでは全件の1↔2ページと People & Body の11↔12ページ、幅390pxでは全件の1↔2ページを、それぞれボタン・ページキーで交互に移動する。高さ600px、各4回のウォームアップ後20回。中央値とp95を記録する。20標本のp95は昇順の `floor(n × 0.95)` 番目（0始まり）、つまり最大値。

ページ内でイベントを起こし、2回目の `requestAnimationFrame` までを測る。実画面への提示時刻やINPではない。ページ内の変更確認とフォーカス確認を行い、各試行後に50ms休止する。CDPのスクリプト・レイアウト・スタイル時間は計測ループの前後で差分を取り、ページ準備のPlaywright操作を含めない。時間によるテストの合否判定は行わず、計測中にビルド・テストを並行実行しない。

LinuxはRyzen 7 3700X、WSL2、Playwright Chromium 153.0.8010.12、CPU 4倍減速。Windowsは専用の一時フォルダー・プロファイルから実際の配布EXEを起動し、Electron 44.4.5 / Chromium 152.0.7977.130、CPU減速なしで比較する。前後はそれぞれ新しいブラウザー・プロファイルを使う。両環境は別々に比較する。

## 検証

追加E2Eは1024px / 390pxでセル寸法の一致、スクロール後の操作欄、画面内への収まり、文字サイズ設定の共有を検証する。表示枠の再利用後も名前・コード・挿入が一致すること、グループ変更、0件、短い最終ページ、Page Up/Downの選択・フォーカス、タグを含むWalesの国旗の挿入を確認する。既存E2Eの文字サイズとページ表示の参照は、非表示で保持する絵文字画面ではなく対象の文字一覧へ限定した。

ビルド・型検査、単体61件、E2E73ケースを確認した。E2Eは初回70件成功、3件の検証対象・操作を調整後に関連28件が成功。書式チェックも成功。Windowsの実際のEXEでもページキー・末尾への選択とフォーカス・完全な国旗シーケンスの挿入を確認し、画面を保存した。


## 二値属性 Emoji との比較による再調査

「文字検索の二値属性 Emoji ではページ送りがそれほど遅くない」という指摘を受け、64件版で再調査した。前の比較は件数・表示文字・フォント等が変わっており、表示密度を原因と断定できるものではなかった。また、2回目のrAFで計測を止めると、その後に発生する描画の反映待ちを取りこぼしていた。

### 確認した追加負荷

全ボタンの `background 0.12s` のCSS transitionが絵文字セルにも適用されていた。文字検索はページ移動で先頭セルを選択するため、同じ表示枠が選択状態を保つ。一方、絵文字は選択したシーケンスを保持するので、ページを進めると枠が非選択、戻ると再選択になる。前回のセル再利用によって、同じボタンの背景色がアニメーションされるようになった。`getAnimations()` で `background-color` の遷移を20回とも確認した。

Windows配布版、1024×768、CPU減速なし、64件の同じページを往復。実際のボタンクリックでフォーカスをページ送りへ移してから計測した。各4回のウォームアップ後20回、操作後2回目のrAFを待ち、さらに50ms休止。アニメーションの有効→無効→無効→有効の順に比較した。

| 条件 | 20回の総時間（待機込み） | 2回目のrAFまでの中央値 | アニメーションを確認した回数 |
| --- | ---: | ---: | ---: |
| 有効 A1 | 3,169.4ms | 27.0ms | 20 |
| 無効 B1 | 2,005.9ms | 25.2ms | 0 |
| 無効 B2 | 1,987.2ms | 21.9ms | 0 |
| 有効 A2 | 3,165.7ms | 28.8ms | 20 |

総時間は約37%短縮した。固定の休止時間1,000msを含む連続操作の結果であり、単一操作の入力遅延とは区別する。遷移を外しても描画自体の負荷は残り、すべてのページが同じ比率で速くなるとは限らない。

### トレースでの切り分け

同じWindows環境の別の診断実行で、20回の往復のトレースを取得した。通常の絵文字一覧はPaintイベント124回、遷移を無効にすると40回。`LayerTreeHost::WaitForCommitCompletion` の合計は約2,235→1,251msだった。これらの待ちがrAF後の休止区間にも発生していた。ラスタライズイベントの経過時間は待ちや並行実行も含むため、GPUの実計算時間やCPU使用時間と同一視しない。

二値属性 Emoji の検索結果も、冒頭の記号類と顔絵文字を含む7〜8ページでは描画負荷が異なった。さらに、検索結果の各ページの先頭64字と同じ順序・Segoe UI Emoji・コードラベルを使う診断用の絵文字データで比較した。文字検索側は残り64セルを非表示にし、128セルの状態更新自体は残るという制約がある。この比較でも、絵文字側の遷移を外すと文字検索側に近い描画負荷となった。単純に「絵文字検索はシーケンスだから遅い」「表示密度だけが原因」とは説明しない。

### 修正と記録

`.emoji-cell` に `transition: none` を指定し、ページ移動・選択時の背景色を即時更新する。文字、色、フォーカスリング、シーケンスの選択・挿入は維持する。計測スクリプトには50msの休止を含む `elapsedMs` と、50ms以上のタスクの回数・合計・最大時間を追加した。2回目のrAFまでの値を、実画面への反映完了時間として扱わない。

比較スクリプトは `var/compare-emoji-search.mjs`、`var/compare-emoji-animation-run.mjs`、Windows実行用は対応する `compare-windows-*.mjs`。結果は `var/windows-emoji-pages-{compare,transitions,animation-run}/result.json`、トレースは `var/emoji-paint-traces/`（管理対象外）。

最終版はビルド・型検査、関連E2E10件、Windows EXEでの6条件の計測と64件表示・ページキー・国旗挿入を確認した。最終計測の原本は `var/windows-emoji-pages-64-paint/result.json`。`elapsedMs` と長いタスクはこの版から記録するため、旧版の2rAFの値とは別の指標として扱う。
