# 基本操作の性能調査と改善

2026-09-25。文字移動、ページ送り、画面切替、検索、編集、文字サイズ変更を本番ビルドで測定した。名前検索と統計画面の再表示を改善した。初回の漢字索引読み込みと長い単一段落の編集には遅さが残る。

## 測定方法

- Ryzen 7 3700X、WSL2/Linux、Node 24.13.0、Playwright Chromium 153.0.8010.12、1024×600。CDP でページの CPU throttling rate を4に設定。ネットワーク減速は使用しない。Windows版の測定とは分ける。
- `npm run build` 後に `node tools/benchmark-operations.mjs [ビルドディレクトリ]` を実行。変更前は `a0e6ccd7` の本番ビルドを `var/operations-before-dist/` に保存した。各実行は新しいブラウザとプロファイルを使う。
- 通常はウォームアップ2回＋20回。初回は別に1回であり、中央値・p95とは呼ばない。名前検索は `LATIN` / `SNOWMAN` の交互実行で、マップの同一条件キャッシュではなく文字検索画面から毎回Workerへ送る。
- ページ内で操作を実行し、非同期検索等は完了を待って2回目の `requestAnimationFrame` までを測る。実画面への提示時刻、INPそのものではない。文字入力は実際の `beforeinput` から2回目の rAF まで。全置換は textarea の値変更＋input イベントで測り、文字入力とは区別する。
- Worker往復は `postMessage` から応答まで。初回のデータ取得・JSON展開・転送等も含み、検索関数だけのCPU時間ではない。`trialMainScriptMs` / `trialLayoutMs` / `trialStyleMs` は準備・画面復帰・自動操作を含む試行全体のCDP集計。Playwrightによるアクセシブル名の取得等も入るため、アプリ単独の処理時間とは解釈しない。
- CPUプロファイルは別の診断実行で取得し、通常の比較測定中はサンプリングしない。測定中に他のテストやパッケージ生成を並行実行しない。時間によるテストの合否判定はしない。

## 比較結果（Linux、CPU減速あり）

同条件で2回ずつ比較し、名前検索・統計再表示の改善を両方で確認した。以下は2回目の前後比較（各20回）。単位はms。p95は昇順の `floor(n × 0.95)` 番目（0始まり）で、20標本では最大値になる。

| 操作 | 中央値 前→後 | p95 前→後 |
| --- | ---: | ---: |
| 文字表内の矢印移動 | 30.7 → 32.5 | 32.9 → 43.3 |
| Page Up / Page Down | 43.7 → 54.8 | 63.4 → 66.6 |
| 統計画面の再表示 | 234.0 → 101.7 | 395.9 → 144.9 |
| 絵文字画面の再表示 | 55.5 → 45.6 | 107.5 → 80.3 |
| 文字検索画面へ移動 | 58.4 → 59.6 | 106.0 → 74.8 |
| 名前検索（LATIN / SNOWMAN） | 269.3 → 115.8 | 315.4 → 159.9 |
| U+323B0直接検索 | 43.7 → 42.5 | 62.6 → 54.0 |
| 部首85で再検索 | 119.2 → 123.8 | 177.5 → 174.5 |
| 日本の出典 J0-3F65 | 66.5 → 74.8 | 85.4 → 86.5 |
| 西夏文字 L2008-0008 | 46.6 → 50.7 | 74.4 → 76.8 |
| 100 UTF-16単位の全置換 | 18.6 → 14.6 | 34.0 → 27.8 |
| 1万 UTF-16単位の全置換 | 86.0 → 80.4 | 118.0 → 100.4 |
| 5万 UTF-16単位の全置換 | 377.8 → 374.3 | 429.4 → 408.2 |
| 約5万単位・改行なしの末尾へ入力 | 528.0 → 523.7 | 572.5 → 541.0 |
| 約5万単位・改行ありの末尾へ入力 | 50.1 → 50.4 | 75.1 → 69.3 |
| 文字サイズ変更 | 30.0 → 37.6 | 51.8 → 61.0 |

名前検索の中央値は約57%、統計画面の再表示は約57%短縮した。名前検索のWorker往復は205.3→29.4ms。初回の比較でもそれぞれ272.9→112.6ms、328.8→104.0msだった。その他の操作はばらつきがあり、一貫した高速化を示す結果ではない。特にページ送りや文字サイズの実装は今回変更していない。

初回操作は各1回で、統計414.5→434.8ms、絵文字454.1→437.9ms、名前検索456.3→226.6ms、漢字部首検索877.6→921.5ms、西夏文字検索98.8→94.3ms。初回の漢字索引読み込みは改善していない。

測定原本は `var/operations-before.jsonl` / `operations-after.jsonl`、再測定は `var/operations-before-repeat.jsonl` / `operations-after-repeat.jsonl`、診断は `var/operations-diagnostic.jsonl` と `var/operations-profiles/statistics-open-warm.cpuprofile` に保存（バージョン管理外）。

## Windows配布版での比較

Windowsローカルの一時フォルダーへ旧版（`release/focus-ring/win-unpacked`）と改善版（`release/operations-performance/win-unpacked`）を別々にコピーし、専用プロファイルでEXEを起動した。Electron 44.4.5 / Chromium 152.0.7977.130、`mojidata://app`、1024×600、CPU減速なし。各2回のウォームアップ後20回を測定した。

| 操作 | 中央値 前→後 | p95 前→後 |
| --- | ---: | ---: |
| 名前検索（LATIN / SNOWMAN） | 267.3 → 80.9ms | 304.3 → 87.2ms |
| 統計画面の再表示 | 55.6 → 41.2ms | 80.6 → 54.6ms |

名前検索は約70%、統計の再表示は約26%短縮した。Linuxの減速環境とは比率も異なるため、それぞれ同一環境の前後比較として扱う。U+323B0のアルゴリズム名、BOMの別名、Page Up/Downとフォーカスリング、統計の集計単位・絞り込み・DOMの保持も確認した。BOMはハングルの正式名にも一致するため、U+FEFFが結果集合に含まれることを検証する。

計測・確認スクリプトは `var/verify-windows-operations-package.mjs`、結果は `var/windows-operations-before/result.json` / `var/windows-operations-after/result.json`。改善後の画面も後者のディレクトリに保存（管理対象外）。検証用プロセス・プロファイルは終了・削除済み。

## 見つかった原因と変更

### 名前検索

従来はコード直接指定・漢字等の候補がない検索で、最大1,114,112コードポイントに対してカテゴリ・名前・別名を照合していた。正式名は46,543範囲の索引としてすでに保持しているため、その表と別名から候補を作り、候補だけを従来の条件判定へ渡すよう変更した。索引の追加ダウンロードや全コードポイントの名前キャッシュは作らない。

CJKや西夏文字等のアルゴリズム名は16進値を展開して照合し、`CJK 323B0` のような検索を保つ。制御文字の正式表示名として使う別名は、別名検索オフでも候補に含む。未割当・私用・サロゲート・非文字の代替名が一致しうる場合は全件走査を残す。漢字等ですでに候補がある場合とコード直接指定の経路は維持する。

19種類のクエリについて、全コードポイントを明示的に渡した全件走査の結果と配列全体が一致することを検証した。部分一致、単語一致、別名無効、アルゴリズム名、複数属性、面、追加版、代替名と未割当を含む。

### 統計画面

「Unicode データ」を開き直すたびにコンポーネントが再生成され、約17万文字の集計と347行の表の生成を繰り返していた。CPUプロファイルでも集計ループ・属性参照とDOM生成が確認できた。

初回だけ遅延読み込みし、その後は `memo` 化した画面を保持して表示・非表示を切り替える。集計単位と絞り込みも保持する。非表示中の文字移動では集計や表生成を繰り返さない。表のDOMを一つ保持する分のメモリを使うが、再表示のたびに増えるキャッシュは作らない。初回の集計・表生成は残る。

## 残る遅さ

- 初回の漢字検索には、22,923,370 bytes の `han-index.json` の取得と展開が含まれる。再検索のWorker往復に比べて初回は数百ms長い。索引分割や生成形式の変更は今回行っていない。
- 改行なしの約5万UTF-16単位を全置換する場合は、CDP集計の大半がレイアウト時間だった。実際の末尾への文字入力でも遅さがあり、同じ混合文字列に110 UTF-16単位ごとの改行を入れると大きく短縮した。ブラウザの長い段落の再配置が主な残存コストで、集計だけを高速化しても大半は解消しない。折返し・文字列の内容・Unicodeの書記素処理を変える回避策は採用していない。
- 統計・絵文字の初回表示は遅延モジュール読込と初期DOM生成を含む。再表示と区別して記録する。初回起動全体や、全端末フォントの取得処理を網羅したベンチマークではない。
