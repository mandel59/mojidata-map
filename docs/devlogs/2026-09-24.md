## 文字サイズ変更の性能改善

- 依頼: 文字サイズスライダーが重いため、スタイル変更で不要な再レンダリングが発生していないか調査・改善。
- 原因: スライダーの React `onChange` が毎回 App の `prefs.size` を更新し、App、128 文字のセル生成、文字詳細、編集バッファまで再実行していた。閉じた詳細検索も、属性レコード 41,319 件や属性範囲を毎回集計・ソートしていた。特にオプション付き `localeCompare` が連続入力 60 回で 226,860 回呼ばれていた。
- `CharacterDisplay` にプレビュー用の state を分離。ドラッグ中は小さなコントロールと文字表のスタイル用コンポーネントだけを更新し、App から受け取った JSX の同一性を保ってセル生成・ほかのツールの再レンダリングを避ける。
- サイズは専用 Context からスタイル用コンポーネントへ渡し、`.character-grid` の `--glyph-size` だけを変更する。CSS 変数を main 全体へ継承させる方式も計測したが、スタイルの再計算範囲を絞れる現在の方式にした。
- ブラウザの native `change` で操作確定時に設定へ反映し、既存の保存処理を使用。React の連続 `onChange` と分離し、ドラッグ終了・キーボード操作に対応。blur / pointercancel も確定を補助する。
- 詳細検索の選択肢は `useMemo` でデータベースごとに集計し、同じ `Intl.Collator` をソート中に再利用。セルの選択位置の存在確認も、各セルではなくページごとに 1 回にした。
- 参考: [React のローカル state と JSX children に関する指針](https://react.dev/reference/react/memo)、[native change イベント](https://developer.mozilla.org/en-US/docs/Web/API/HTMLElement/change_event)。

## 小型ノートPC向けの UI 整理

- 依頼: 見やすさを保ちながら UI の占有面積を減らし、必要な機能を小型画面に収める。確認した主対象は 1024×600〜1366×768 の小型ノートPC。
- 実装前の測定では 1024×600 / 1366×768 ともページ高が 1,388px、編集欄の開始位置が約 1,099px。大きなヘッダー、独立したツールタブ、設定欄、常設サイドバー、編集操作の縦積みが原因だった。
- ヘッダーをアプリ名・ツール切替・メニューの1行にし、キャッチコピー、大きなロゴ、英語の補助見出し、重複説明、常設フッターを省略。版情報・クレジット・使い方・配色・最前面表示はアプリメニューへ移した。
- 常設の左サイドバーを廃止し、面とブロックの選択を文字表上部に配置。「一覧」で名前の絞り込みと予約面切替を開ける。ブロックの選択肢は一覧の絞り込み状態に依存しない。
- 「詳細検索」「コード指定」「表示設定」「変換・保存」を native Popover API に移した。外側クリック・Escape で閉じ、Escape 後のフォーカス復帰を検証。詳細検索には設定中の条件数を表示し、Ctrl/Cmd+F は開いたポップオーバーを閉じて検索欄へ移動する。

## 制御文字のコピー結果を確認

- 制御文字のコピー時に表示用の印刷文字が混ざるという報告を調査。文字情報は `String.fromCodePoint(cp)`、編集バッファは元のテキストをコピー API に渡しており、`db.glyph()` の表示用記号はコピー用データに使っていないことを確認。
- ユーザーから、Windowsでの制御文字の表示方法によるものかもしれないとの補足があったため、実装変更に先立って実際のクリップボード内容を検証した。
- 隔離した Linux / Xvfb / Electron の環境で U+0001、U+0009、U+000A、U+000D、U+001B、U+007F、U+0085 を選び、文字情報の「コピー」と、バッファへの追加後の「コピー」の計14通りを確認。クリップボードから読み出した値は、いずれも元の制御文字と一致した。例えば表示 `␛` に対してコピー結果は U+001B であり、U+241B ではなかった。
- 不具合はこの経路では再現せず、アプリコード・配布物は変更しない。Windows 実機での貼付先の描画は未確認。調査用スクリプトと結果は `var/probe-control-copy.mjs` / `var/control-copy-result.json` に保存（バージョン管理外）。

## 文字マップのページ送りの性能調査

- 依頼: ページ送りが重い原因と、使用している内部表現の確認。今回は原因調査と比較実験を行い、製品コード・配布物は変更しない。

### 内部表現

- コードポイントは JavaScript の `number`。文字列にする箇所では `String.fromCodePoint()` を使い、文字列自体は JavaScript の UTF-16 表現となる。
- `public/data/unicode.json` は 6,276,775 bytes。JSON を通常の JavaScript 配列・オブジェクトへ展開する。名前46,543範囲、基本レコード41,319範囲、属性90種類・計53,958範囲を持ち、全コードポイント分の文字オブジェクトを展開する方式ではない。
- 属性は名前をキーとするオブジェクトの下に、開始点順の `[start, end, value]` 配列を置く。例: Block の `[12352, 12447, "Hiragana"]`（U+3040〜U+309F）。基本レコードも開始・終了とカテゴリ等の列を持つ配列。`inRanges()` で二分探索し、属性の既定値は別の範囲表から補う。
- 文字表は `pageStart` から128個の整数を作り、React で128個の button とその子 span を描画する。Canvas ではない。ブックマーク・検索結果も整数配列で保持し、表示する128件を切り出す。
- 検索は Worker が担当するが、ページ送り・属性参照・DOM 更新はメインスレッドで行う。通常データはロード済み Promise をキャッシュ。Unihan はコードポイント上位部分ごと（4,096コードポイント幅）の JSON を遅延読込する。メインと Worker はそれぞれの実行環境にデータを保持する。

### 計測した負荷

- Linux headless Chromium、本番ビルド、1024×600、CPU 4倍減速。U+3000台の隣接2ページをウォームアップ後に往復した。診断用の React DevTools hook、DOM MutationObserver、CDP Performance / CPU Profiler を使用。
- 20回のページ変更で App / CharacterGrid / Editor は各20回、CharacterDetails は40回更新。button が2,560個削除され、2,560個追加された。文字セルの `key` がコードポイントであるため、ページが変わると128個とも新しい要素になる。
- 同じ20回で追加リクエストは0件。基本データの再取得や Unicode 全体の検索は走っていない。
- CPU サンプルでは `scrollIntoView()` 内の処理が目立つ。DOM 更新直後の位置計算に伴うレイアウト確定を含む。これを一時的に無効化した比較は中央値75.6ms→71.4msに留まり、呼び出しを消すだけでは描画コストは解消しない。
- 文字表を診断目的で `display:none` にした比較は約75.6ms→33.7ms。データ参照と React のセル生成は継続する一方、レイアウト・スタイル処理が大きく減った。表示側の負荷が大きいことを確認した。
- CharacterDetails は選択更新に加え、Unihan / 異体字データの状態更新でも再評価される。閉じた属性一覧を含めて `db.details(cp)` と JSX を作り直す。
- Editor はバッファが変わらないページ変更でも検証・符号化・文字数集計を再実行する。ASCII 1万文字を入れた比較では、CPU プロファイル内で `textStats()` の負荷が増え、更新待ち中央値は80.2ms→109.5msだった。
- 読み込んだフォントを保持する非表示 FontPanel もページ変更ごとに再評価される。glyph / SVG の計算は依存値で memo 化されているが、cp が変わると glyph 参照が更新される。フォント読込後のケースはフォント描画条件も変わるので、差分をすべて非表示パネルの計算時間と解釈しない。

### セル再利用とデータ参照の比較

- `var/reused-cells-dist/` にだけ診断用ビルドを作成。文字セルのキーをコードポイントから表示枠の index に変更し、実アプリのソースと `dist/` は変更していない。CPU サンプリングと参照回数のラップを外した比較を40ページ変更で実施した。

| ケース | 更新待ち中央値 | p95 | 先頭セルの DOM 再利用 |
| --- | ---: | ---: | ---: |
| 現行 | 70.8ms | 99.9ms | 0 / 40回 |
| 固定枠を再利用する実験 | 62.2ms | 89.0ms | 40 / 40回 |

- 128文字分の category / Block / name×2 / glyph と、詳細2回のデータ参照だけを別に200回計測すると、現行ケースの中央値0.4ms・p95 1.0ms。この単独ループの結果を UI 全体の時間から単純に差し引けるわけではないが、範囲配列の二分探索をまず置き換える根拠は見られなかった。
- 更新待ちは click の実行から2回目の requestAnimationFrame までの時間で、実画面への提示遅延そのものではない。数値は同一環境での比較用で、Windows 実機やすべての文字・フォントへ一般化しない。
- 改善の優先候補は、編集欄・非表示ツール・設定一覧の更新分離、セルDOMの再利用、詳細欄の重複更新削減、文字表のレイアウト範囲の限定。セル再利用単独の効果は限定的で、文字の配置・描画コストは残る。
